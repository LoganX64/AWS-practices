# AWS Pricing

AWS pricing is important because AWS is mostly usage-based.
we don't generally buy AWS infrastructure upfront; we pay for the resources and services we use.
Goal is not memorize AWS pricing instead to understand -
`what causes AWS costs and how to estimate and control them.`

## Pay-as-you-go

The basic AWS pricing model is:

`Use resources → AWS measures usage → you pay according to the service's pricing model.`

eg: when we run a EC2 instance:

```
EC2 Instance
     │
     ├── Instance running
     │       ↓
     │    Compute cost
     │
     ├── EBS volume
     │       ↓
     │    Storage cost
     │
     └── Data transfer
             ↓
          Possible cost
```

imp: `Different components can generate charges.`

## AWS pricing is service-specific

There isn't one universal AWS price.

Each service has its own pricing model.

```
| Service     | Common pricing dimension                       |
| ----------- | ---------------------------------------------- |
| EC2         | Instance type + running time                   |
| S3          | Storage + requests + data transfer             |
| RDS         | DB instance + storage + other usage            |
| Lambda      | Requests + compute duration                    |
| DynamoDB    | Capacity/requests + storage                    |
| CloudFront  | Data transfer + requests                       |
| EBS         | Provisioned storage + other applicable usage   |
| NAT Gateway | Hourly + data processed                        |
| CloudWatch  | Metrics/logs/other features depending on usage |
```

imp: `Always check the pricing page for the specific service.`

## Main AWS pricing dimensions

Several types of usage commonly affect your bill.

### Compute

We pay for compute capacity.

```
EC2
 ↓
t3.micro
 ↓
Running for a period of time
 ↓
Compute charge
```

### Storage

we may pay for storing data.

```
S3
│
├── 10 GB
├── 100 GB
└── 1 TB
```

More stored data generally means more storage cost.

### Requests

Some services charge based partly on the number of requests/API operations.

eg:

```
Application
    │
    ├── S3 PUT
    ├── S3 GET
    ├── S3 GET
    ├── S3 PUT
    └── ...
```

A large application generating huge numbers of requests can therefore have request-related costs.

### Data transfer

Moving data can generate charges depending on where the data is going.

eg :

```
EC2
 │
 ├── Internal AWS traffic
 │
 ├── Internet
 │
 └── Another AWS service
```

The pricing depends on the specific path and service.

This is an important topic when designing production architectures.

### Provisioned capacity

Some services charge based on capacity you provision.

a database may have:

```
Database
   │
   ├── Compute capacity
   ├── Storage
   └── I/O / requests / other usage
```

Depending on the service and configuration, you may pay even when the resource isn't heavily utilized.

## AWS Free Tier

AWS provides Free Tier benefits.
Free usage is subject to:

- service
- amount of usage
- account eligibility
- time period
- specific pricing terms

eg: a service may have a certain amount of usage included under a Free Tier offer, while usage beyond that can be charged.Always check the current AWS pricing/Free Tier terms before relying on them.

## Very important: "Stopped" doesn't always mean "free"

This is a common beginner mistake.

Suppose we have:

```
EC2
 └── Instance
      └── EBS volume
```

we stop the EC2 instance.

The compute instance may stop accumulating its normal running compute charges, but the attached EBS storage can still incur charges.

so:

```
EC2 stopped
   │
   ├── Compute → generally stops
   │
   └── EBS → storage can still cost money
```

Similarly, other AWS resources may continue generating charges even when your main application isn't running.

Beginner rule -

`Don't assume "stopped" means "no bill."`

## Example: running a small Go API

Imagine you deploy :

```
                 Internet
                    │
                    ▼
                 EC2
               Go API
                    │
             ┌──────┴──────┐
             ▼             ▼
          RDS             S3
       PostgreSQL        Files
```

Potential cost areas:

```
EC2
 ├── Compute
 └── EBS storage

RDS
 ├── DB instance
 ├── Storage
 └── Other applicable usage

S3
 ├── Storage
 ├── Requests
 └── Data transfer

Network
 └── Applicable data transfer
```

So when estimating the application's AWS cost, don't look at only the EC2 price.

## Region can affect pricing

The same type of AWS resource can have different pricing depending on the Region.
This is one reason Region selection isn't only about latency and availability.
You should consider:

- pricing
- latency
- service availability
- data residency
- compliance
- architecture requirements

## On-demand pricing

On-Demand means we pay for usage without committing to a long-term capacity commitment.

`Use it when we need it, pay according to usage.`

This is often useful when:

- learning
- experimenting
- workloads are unpredictable
- we don't want a long-term commitment

## Reserved/commitment-based pricing 3

AWS also offers pricing models involving commitments.

basic idea is:

`Commit to certain usage/compute characteristics → potentially receive lower effective pricing.`

## Spot Instances

EC2 also has Spot Instances.

`Use spare AWS compute capacity at potentially lower prices, but the workload must tolerate interruption.`

Good candidates can include:

- batch processing
- temporary workloads
- fault-tolerant workers
- CI workloads
- distributed processing

Not ideal for something that requires uninterrupted execution unless our architecture handles interruption appropriately.

## AWS Pricing Calculator

AWS provides a Pricing Calculator for estimating costs.This is useful before deploying a production architecture.

`How much does this architecture cost?`

Common cost-optimization techniques include:

### Right-sizing

instead : Appropriate EC2

### Delete unused

### Use budgets and billing alerts

AWS provides tools for monitoring and controlling spending.

## Cost vs architecture

A more sophisticated architecture isn't automatically cheaper.

For eg:

Simple

```
Internet
   ↓
EC2
   ↓
PostgreSQL
```

More production-oriented

```
Internet
   ↓
CloudFront
   ↓
Load Balancer
   ↓
Multiple EC2
   ↓
RDS Multi-AZ
```

The second architecture can provide additional availability/scalability features, but it also introduces more resources and potentially more costs.

Therefore:

`Choose architecture based on requirements, then optimize its cost.`

```
                 AWS Account
                     │
             ┌───────┴────────┐
             ▼                ▼
          Services          Usage
             │                │
     ┌───────┼───────┐        │
     ▼       ▼       ▼        │
    EC2     S3      RDS       │
     │       │       │        │
     └───────┴───────┴────────┘

```

The key question is:

`What resources am I running, and what usage does each resource generate?`

## Important AWS cost terms

```
| Term               | Meaning                                         |
| ------------------ | ----------------------------------------------- |
| Pay-as-you-go      | Pay based on usage                              |
| On-Demand          | Use without long-term commitment                |
| Free Tier          | Limited eligible usage under specified terms    |
| Reserved Instances | Commitment-based EC2 pricing option             |
| Savings Plans      | Commitment-based pricing model                  |
| Spot               | Discounted spare compute with interruption risk |
| Pricing Calculator | Estimate AWS costs                              |
| Right-sizing       | Match resource size to workload                 |
| Data transfer      | Cost considerations for moving data             |
```

```
AWS primarily uses usage-based pricing, where costs depend on the service and factors such as compute, storage, requests, provisioned capacity, and data transfer. Different Regions and pricing models can have different costs, so AWS Pricing Calculator and cost-monitoring tools are useful for estimating and controlling spending.
```

`AWS cost = What you run + How much you use + How long you use it + How data moves.`
