# AWS Service Selection

AWS has 200+ services, so an important AWS skill is knowing:

`'Given a problem, which AWS service should I use?'`

Need to understand the job each service performs and the trade-offs involved.

## 1. Start with the problem, not the service

Don't think:

`"Should I use EC2 or Lambda?"`

First think:

`"What does my application need?"`

eg:

```
Requirement:
Run my Go REST API
        ↓
Need compute
        ↓
Possible choices:
EC2 / ECS / Lambda / EKS
        ↓
Choose based on requirements
```

This is the correct AWS mindset.

## 2. A simple service-selection framework

When choosing an AWS service, ask:

```
1. What am I trying to build?
        ↓
2. What type of resource do I need?
        ↓
3. How much infrastructure do I want to manage?
        ↓
4. What are my scalability requirements?
        ↓
5. What are my availability requirements?
        ↓
6. What are my security requirements?
        ↓
7. What does it cost?
        ↓
8. Is the service available in my Region?a
```

## 4. Compute selection

Suppose we need to run a Go application.
we could choose: `EC2,
Lambda,
ECS,
EKS`

The question is why we would choose each.

### EC2

Choose EC2 when we want a virtual server and significant control.we manage more of the environment.

Good when we need:

- OS-level control
- custom software
- long-running applications
- traditional server architecture
- specialized configurations

### Lambda

Choose Lambda when our application can naturally run as functions/events.

Good for:

- event-driven workloads
- short-running functions
- scheduled jobs
- APIs with suitable workloads
- background processing

### ECS

Choose ECS when we want to run Docker containers without adopting Kubernetes.

Good when:

- our application is already containerized
- we want AWS-managed container orchestration
- we don't need Kubernetes specifically

### EKS

Choose EKS when you specifically need Kubernetes.

Good when:

- Kubernetes is a requirement
- we need Kubernetes ecosystem/tooling
- our organization already operates Kubernetes
- portability across Kubernetes environments matters

## 5. Compute decision tree

A simple starting point:

```
Need to run application?
        │
        ▼
Do I need a virtual server?
        │
       Yes
        ↓
       EC2
        │
       No
        ↓
Is it containerized?
        │
      Yes
        ↓
Do I specifically need Kubernetes?
      /   \
    Yes    No
     ↓      ↓
    EKS    ECS
```

If the workload is function/event-oriented:

```
Event / Function  -> Lambda
```

This is only a starting framework—not a universal rule.

## 6. Storage selection

Suppose our Go API needs to store data.

`'What kind of data am I storing?'`

### S3 — Objects/files

Use S3 for:

- images
- PDFs
- videos
- backups
- logs
- static files

### EBS — Disk for EC2

EBS is like a virtual disk attached to compute resources such as EC2.

```
EC2
 │
 └── EBS
      │
      └── filesystem/data
```

### EFS — Shared filesystem

EFS is useful when multiple compute resources need access to a shared filesystem.

```
EC2 ───┐
       │
EC2 ───┼── EFS
       │
EC2 ───┘
```

## 7. Database selection

This is one of the most important decisions.

First ask:

`"What data model do I need?"`

### RDS

Choose RDS when we need a managed relational database. eg: PostgreSQL,MySQL,MariaDB,Oracle,SQL Server.

### Aurora

Aurora is an AWS relational database engine compatible with PostgreSQL/MySQL.

### DynamoDB

Choose DynamoDB when a managed NoSQL key-value/document model fits the workload.

### ElastiCache

Choose ElastiCache when we need an in-memory cache.

## 8. Networking selection

Suppose users need to access our Go API.

we might use: `Route 53, CloudFront, ELB,VPC`
But they solve different problems.

### VPC

Our AWS network.

```
AWS
└── VPC
    ├── Subnets
    ├── Route tables
    ├── Security groups
    └── Network connectivity
```

### Route 53

DNS.

### ELB

Distributes traffic across targets.

### CloudFront

CDN/edge delivery.

Useful for:

- static assets
- cached content
- global content delivery
- reducing latency for users far from the origin

## 9. Security service selection

If the problem is:

`"Who can access AWS resources?"`

Use:

```
IAM
```

`"How do I encrypt/manage keys?"`

Use:

```
KMS
```

`"Where should I store passwords/API keys?"`

Use:

```
Secrets Manager
```

`"How do I filter malicious web requests?"`

Use:

```
WAF
```

## 10. Monitoring service selection

### CloudWatch

Use when we want to know:

`"What is happening with my application?"`

eg:

- CPU metrics
- application logs
- alarms
- dashboards
- operational monitoring

### CloudTrail

Use when we want to know:

`"Who performed an AWS API/account action?"`

eg:

```
Who changed this security group?

CloudTrail
     ↓
User/role
     ↓
Action
     ↓
Time
     ↓
Resource
```
